# 幽灵整理记录（GhostTransferCleaner）

MoviePilot 插件：体检「整理记录还在、但媒体文件实际上已不在媒体库」的幽灵记录，
支持一键清理，让同类资源重新下载后能正常自动整理入库。

**判定依据是 NAS 本地 strm 文件，不访问 115 或任何云端接口**（避免风控）。

---

## 一、它解决什么问题

MP 自动整理的判定逻辑是：**只要存在一条整理成功的历史记录，就直接跳过整理**
（v2 源码 `app/chain/transfer.py` 中日志原文：`已成功转移过，如需重新处理，请删除历史记录`）。

所以一旦媒体文件被误删、而整理记录仍留在库里，再次下载同一资源时，
MP 会因为「已有整理记录」而跳过整理，表现为**下载完成了但媒体库始终不入库**。

本插件扫描全部整理记录，逐条核对它在媒体库里是否还有对应媒体，
把「记录还在、媒体已没了」的记录列出来，可人工确认后清理。

> 清理只删除数据库里的整理记录，**不删除任何媒体文件**。

---

## 二、判定依据：只比对 NAS 本地 strm

媒体库为 strm 形态时，**一个 strm 文件对应云端（115）一个媒体文件，两者默认一一对应**。
因此判断一条整理记录是否还有效，只需要看它记录的目标路径在本地 strm 目录里
还能不能找到对应文件——完全不需要访问云端。这样做有三个好处：

- **不碰 115**：不会触发风控；
- **快**：只读本地文件系统，按需枚举目录并缓存；
- **稳**：不受云端接口限流、抖动影响。

### 匹配方式：后缀匹配

把记录里的目标路径逐级剥掉前导目录，拼到每个 strm 根目录下查找同名 `.strm`。
例如记录里是 `/115/Movies/流浪地球 (2019)/流浪地球 (2019) - 2160p.mkv`，
strm 根目录是 `/media/strm`，会依次尝试：

```
/media/strm/115/Movies/流浪地球 (2019)/流浪地球 (2019) - 2160p.strm
/media/strm/Movies/流浪地球 (2019)/流浪地球 (2019) - 2160p.strm   ← 命中
/media/strm/流浪地球 (2019)/流浪地球 (2019) - 2160p.strm
/media/strm/流浪地球 (2019) - 2160p.strm
```

所以「记录里是 115 路径、本地是另一个 strm 目录」这种前缀不一致的情况无需额外配置。
同时扩展名会自动换算（`.mkv`/`.mp4`/无扩展名 → `.strm`），名称比较大小写不敏感。

如果记录的路径与本地目录**中间层名字**也不一致（例如记录是 `/115/归档/某片`、
本地在 `/media/strm/电影二区/某片`），可用配置里的「路径前缀映射」修正。

### 判定分级

| 分级 | 判定条件 | 说明 |
| --- | --- | --- |
| 正常 | 目标路径在 strm 库中能找到对应 strm | 不需要处理 |
| 整部缺失 | strm 目录树里连该节目目录都找不到 | 整部媒体都没了，可信度最高，默认可自动清理 |
| 局部缺失 | 节目目录还在，但该文件对应的 strm 不存在 | 可能只删了其中几集，建议人工确认 |
| 无法判断 | 记录里没有目标路径，或未配置 strm 根目录 | 跳过，不参与清理 |

两点补充：

- **strm 文件存在、但本地没有对应视频文件，属于正常**（strm 形态的常态），
  不会被判为幽灵；判定只认 strm。
- 打开「深度检查」后，会额外读取记录里的 `files` 文件清单，
  逐个核对是否还有对应 strm；当记录中的文件已全部没有 strm 时也会判为幽灵。
- 只检查**整理成功**的记录（失败记录不会触发跳过逻辑，不需要清理）。

### 安全护栏

1. 「一键清理」需要先在插件配置里显式打开 **允许一键清理** 开关，否则页面按钮不会真正删记录。
2. 默认只清理 **整部缺失** 的记录（可按需关闭该限制）。
3. 若一次扫描中超过 **八成** 的记录都找不到对应 strm（样本 ≥ 20 条），
   插件会认为这更像「strm 根目录配置有误」而不是文件被删，**自动中止清理** 并在页面/通知里提示。
4. 单次扫描最长 60 秒，超时自动结束并标注结果可能不完整。

## 三、看不懂结果？先看诊断报告

汇总数字（「发现 5000 条幽灵记录」）回答不了最关键的问题：**到底是文件真被删了，
还是 strm 目录根本没配对**。点数据页面上的 **生成诊断报告**，会产出一份可直接复制的
纯文本报告，把「记录里的路径」和「strm 库里的实际目录」逐条摆在一起对照。

报告分七节：

| 小节 | 内容 |
| --- | --- |
| 一、结论 | 先用两三句话点明「是配置问题」还是「确实被删了」，并明确要不要清理 |
| 二、配置快照 | 当前 strm 根目录、前缀映射、各开关，以及最近一次扫描结果 |
| 三、strm 媒体库体检 | 每个根目录是否存在、顶层有哪些目录、目录名索引规模、`.strm` 文件总数 |
| 四、整理记录侧画像 | 记录总数、目标路径的顶层目录分布、文件扩展名分布 |
| 五、逐条对照 | 抽查若干条记录，逐级列出「试过哪些相对路径」「该层目录是否存在」「目录里实际有什么文件」 |
| 六、交叉命中统计 | 文件名命中数、末级目录名命中数，以及记录顶层目录与 strm 顶层目录的交集 |
| 七、建议 | 按命中情况给出的具体整改方向（多数情况是可直接照抄的「路径前缀映射」） |

其中最有用的是两组信息：

- **逐级尝试的明细**——能直接看出记录路径是在哪一级开始对不上的，以及那一级目录里
  真实存在什么文件名（命名规则差异会立刻暴露）；
- **「记录里的目录名在 strm 库中的落点」**——反查记录中每一级目录名在 strm 库里
  对应哪个真实路径，一眼就能判断是「根目录填错」还是「层级不同」。

报告只读本地文件系统与整理记录，同样不访问云端；会同时写入 MP 日志（一条记录，不刷屏）
并保存在插件数据里，重启后仍可查看。

> 报告的作用是**在你动手清理之前**把判断依据摊开。若报告结论是「两边毫无交集」，
> 请先核对配置，不要清理。

### 报告怎么送到你手上：后台生成 + 通知推送

报告要遍历 strm 目录树，媒体库大时可能耗时几十秒。而 **MoviePilot 前端的事件处理是
"接口异常就只在浏览器控制台打日志"**（`PageRender.vue`：`catch (error) { console.error(error) }`，
没有任何弹窗），接口一慢或一报错，页面就会表现为**「点了按钮没反应」**。

所以本插件把「生成」和「交付」拆开：

1. 点 **生成诊断报告** 后接口**立刻返回**，报告在后台线程里生成，页面不再干等；
2. 生成完成后**自动推送到 MP 通知渠道**，手机直接能看到；
3. **无论成功还是失败都会推送**——失败时连错误原因一起发出来，
   不会再出现「点了没反应、也不知道哪里错了」；
4. 完整报告同时写入插件目录的 `diagnose_report.txt`，并整篇打进 MP 日志
   （搜 `幽灵整理记录｜诊断报告` 可看全文）。

通知正文按重要性排序，**结论 → 逐条对照（前 3 条）→ 建议 → 交叉命中统计**，
开头第一行是该报告的生成时间，末尾给出完整报告的位置。不同渠道长度限制不同，
若你的渠道偏短（例如企业微信），被截掉的是最末尾的统计部分，
**结论与建议一定在最前面**。

也可以不依赖页面：发送远程命令 `/ghostdiag` 同样能触发并收到通知。
生成完一次之后，页面上还有 **把报告发到通知** 按钮，可随时重发（内容取已保存的报告，
重启插件后依然可用）。

## 四、安装

插件按 MoviePilot **v2** 的插件接口编写（已对照 v2.15.6 源码：`app/plugins/__init__.py`、
`app/db/models/transferhistory.py`、`app/db/transferhistory_oper.py`、前端 `PageRender.vue`）。

### 方式 A：从插件仓库安装（推荐）

1. 把插件仓库地址加入 MP 的插件市场（MP → `设定` → `系统` → `进阶设置` → **插件市场地址**，
   多个地址用英文逗号分隔）：

   ```
   https://github.com/yuwancumian2009/MoviePilot-Plugins
   ```

2. `插件` 页面 → 插件市场 → 搜索「幽灵整理记录」→ 点击 **安装**。
3. 进入插件，填写 **strm 媒体库根目录**，打开「启用插件」并保存。

该插件在仓库中的元数据写在 `package.v2.json`，源码在 `plugins.v2/ghosttransfercleaner/`，
`release` 为 `false`，也就是**直接从仓库源码安装**，不依赖 GitHub Release 压缩包。

### 方式 B：本地插件仓库（不联网也能用）

1. 在 MP 持久化的 config 目录下建一个本地插件仓库，放入：

   ```
   <你的 moviepilot/config 目录>/pluginrepo/
       package.v2.json
       plugins.v2/ghosttransfercleaner/__init__.py
   ```

2. MP → `设定` → `系统` → `进阶设置` → **本地插件仓库路径**，
   填容器内路径（例如 `/config/pluginrepo`），保存。
   （也可以用环境变量 `PLUGIN_LOCAL_REPO_PATHS`，多个路径用 `,` 分隔）
3. 重启容器（若已开启 `PLUGIN_AUTO_RELOAD` 插件热加载，可省去重启）。
4. 插件市场 → 本地插件 → 安装 → 启用。

> 这种方式插件代码在持久目录里，容器更新不会丢。

### 方式 C：直接拷进容器（临时验证用）

1. 把插件目录拷进容器，注意**目录名必须是类名的小写**：

   ```bash
   docker cp ghosttransfercleaner <容器名>:/app/app/plugins/
   ```

2. 重启容器：

   ```bash
   docker restart <容器名>
   ```

3. 插件市场左侧 **本地插件** → 找到「幽灵整理记录」→ 点击 **安装** → 启用。

> 缺点：插件代码位于容器内，拉新镜像重建容器后会丢失，需要重新拷一次。

## 五、使用

### 必填配置：strm 媒体库根目录

插件必须知道 strm 文件放在哪里，否则**不会给出任何结论**（数据页面会提示未配置）。

| 配置项 | 示例 | 说明 |
| --- | --- | --- |
| strm 媒体库根目录 | `/media/strm` | 填 **容器内**可访问的路径，每行一个，可配多个 |
| 路径前缀映射（可选） | `/115/归档=/media/strm/电影二区` | 每行一条 `记录中的前缀=本地实际前缀`；不填时会自动后缀匹配，多数情况无需配置 |

> ⚠️ **只填存放 strm 文件的本地目录**。不要填 115、WebDAV、CloudDrive 等网络挂载路径，
> 否则读目录同样会打到云端，就失去了规避风控的意义。

容器内找不到路径时，可以先 `docker exec -it <容器名> ls /media/strm` 确认一下挂载。

### 数据页面

打开插件即可看到统计概览、幽灵记录清单（最多展示 200 条）和四个按钮：

- **立即扫描**：重新体检一次，完成后页面自动刷新。
- **清理幽灵记录**：按当前配置清理（需先开「允许一键清理」）。
- **生成诊断报告**：后台生成一份诊断报告（见第三节），完成后推送到通知渠道；
  稍后刷新页面可看到报告全文（等宽字体展示，可长按选择复制）。
- **把报告发到通知**：把最近一次生成的报告摘要重新推送到通知渠道，随时可重发。

### 常用配置

| 配置项 | 默认 | 说明 |
| --- | --- | --- |
| 启用插件 | 关 | 总开关 |
| 扫描后发送通知 | 开 | 扫描完成后推送到已配置的通知渠道 |
| 诊断报告生成后发送到通知渠道 | 开 | 关闭后报告只落盘与写日志，不推送 |
| 深度检查 | 关 | 额外按记录内的文件清单逐个核对 strm（见判定规则） |
| 只清理「整部缺失」的记录 | 开 | 关闭后会连「局部缺失」一起清理，请谨慎 |
| 允许一键清理 | 关 | 打开后数据页面的清理按钮才生效 |
| 定时扫描时自动清理 | 关 | 配合下面的 cron 使用 |
| 只检查 N 天前的整理记录 | 0 | 0 表示全部；可用于避开刚整理完的记录 |
| 单次最多检查记录数 | 5000 | 防止记录过多时扫描过慢 |
| 定时扫描 cron | 空 | 例如 `0 */6 * * *` 表示每 6 小时一次 |
| 保存后立刻扫描一次 | 关 | 保存配置后自动跑一次，自动复位 |

### 远程命令

| 命令 | 说明 |
| --- | --- |
| `/ghost` | 立即体检并推送结果通知（可在通知渠道/机器人里直接发送） |
| `/ghostdiag` | 生成诊断报告并推送到通知渠道（不依赖页面按钮的入口） |

### REST 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/v1/plugin/GhostTransferCleaner/status` | 查询最近一次扫描结果 |
| GET/POST | `/api/v1/plugin/GhostTransferCleaner/scan` | 立即扫描 |
| GET/POST | `/api/v1/plugin/GhostTransferCleaner/clean` | 清理（需开启「允许一键清理」） |
| GET/POST | `/api/v1/plugin/GhostTransferCleaner/diagnose` | 触发后台生成诊断报告（**立即返回**，结果走通知渠道） |
| GET/POST | `/api/v1/plugin/GhostTransferCleaner/notify_report` | 把已生成的报告摘要重发到通知渠道 |

> `diagnose` 是**异步**接口：它只负责启动，不在响应里返回报告正文。
> 想拿全文，请看通知、插件目录的 `diagnose_report.txt` 或 MP 日志。

调用需带 MP 的 API Key（`apikey` 参数/请求头）或登录令牌。

### 验证是否生效

清理后重新下载一次该资源，若 MP 日志中不再出现
`已成功转移过，如需重新处理，请删除历史记录`，即说明整理链路已恢复正常。

## 六、兼容性与实现说明

- 目标运行版本：MoviePilot v2（含 v2.15.6；旧版 v2 无 `src_storage`/`dest_storage` 也能正常工作）。
- 只使用长期稳定的公开接口：`app.plugins._PluginBase`、`app.db.SessionFactory`、
  `app.db.models.transferhistory.TransferHistory`、`app.schemas.types.EventType`。
- **不导入 `app.chain.storage`，不做任何云端/远端存储查询**，只读本地文件系统
  （离线测试里有一条回归用例专门校验这一点）。
- 目录内容按需枚举并缓存，同一次扫描内不重复读同一目录。
- 诊断报告会重新枚举一次 strm 目录以建立「目录名索引」与「文件名索引」，
  两者都有条目数与耗时上限（超限会在报告里标注），不会因为媒体库很大而卡住。
- 诊断报告在**后台线程**生成、通过通知渠道交付，因此不会因为耗时被前端判定成无响应；
  报告失败也会推送错误原因，不会静默。
- 报告分节与通知裁剪都以**行首的 `【`** 为界（报告正文里也会出现 `【】`，
  例如结论中的「这【不是「媒体被删」的特征】」），避免把一节正文截断。
- 升级后，旧版本（v1.0.0，基于存储层查询）的扫描结果会被自动丢弃，避免误读。
- 页面全部用 Vuetify 声明式 JSON（默认渲染模式），不引入任何前端构建产物，也不改动 MP 现有界面。
- 不注册 `PluginReload` 等侵入式回调，不修改任何 MP 原有数据表结构。

_tests/

```

测试台覆盖扫描判定、分级、清理护栏、旧表结构兼容、路径映射、诊断报告与通知交付等，

```
